# PRD — Football Newsroom

## ۱. مسئله

بررسی دستی ده‌ها منبع فوتبال زمان‌بر است. اخبار بارها بازنشر می‌شوند و تشخیص خبر اصلی، اعتبار، تازگی و اهمیت دشوار است.

تولید روزانه پادکست نیازمند: بررسی منابع، حذف تکراری، تشخیص معتبر، تفکیک شایعه/رسمی، انتخاب رویداد، ترتیب روایت، متن گفتاری، بررسی نام/عدد/نتیجه، تولید و انتشار صوت است.

این محصول باید این فرایند را **خودکار و قابل‌کنترل** کند.

## ۲. چشم‌انداز

اتاق خبر هوشمند که مانند تیم کوچک خبری عمل می‌کند؛ تصمیم نهایی زیر کنترل سردبیر انسانی.

## ۳. اهداف محصول

### اصلی

- کاهش زمان جمع‌آوری و بررسی اخبار
- کاهش خبرهای تکراری
- افزایش اعتبار خروجی
- حفظ منبع هر ادعا
- تولید منظم پادکست
- کاهش و شفافیت هزینه مدل‌ها
- امکان جایگزینی مدل‌ها
- تاریخچه کامل تصمیم‌های سردبیری

### فرعی (پس از v1)

خلاصه متنی، Push Notification، نسخه تلگرام/شبکه‌های اجتماعی، تیتر کوتاه، توضیح اپیزود، خبرنامه ایمیلی.

## ۴. خارج از محدوده نسخه اول

- پخش زنده مسابقه / خرید حق پخش
- شرط‌بندی / پیش‌بینی مالی
- شبکه اجتماعی عمومی / کامنت عمومی
- استریم ویدئو / فروش اشتراک عمومی
- تولید محتوای ویدئویی کامل

## ۵. کاربران و قابلیت‌ها

نگاه کنید به `PRODUCT_OVERVIEW.md` بخش کاربران. نقش‌های RBAC اولیه:

| Role | دسترسی کلیدی |
|------|-------------|
| `system_admin` | همه تنظیمات، کاربران، کلیدها، health |
| `editor` | inbox، events، episodes، approve/reject |
| `reporter` | افزودن خبر/منبع، تناقض، پیشنهاد امتیاز |
| `content_manager` | اپیزود، لحن، صوت، انتشار |

## ۶. نیازمندی‌های کارکردی (v1)

### FR-SRC — منابع

- CRUD منبع با نوع، کشور، زبان، RSS/Sitemap/Base URL، قوانین استخراج، فاصله بررسی، اعتبار اولیه، پوشش تیم/لیگ، اولویت، JS نیاز، rate limit
- مشاهده آخرین اجرای موفق و خطاهای اخیر
- فعال/غیرفعال‌سازی

### FR-CRAWL — کشف و دریافت

- زمان‌بندی بررسی منابع
- کشف URL جدید، دانلود HTML، ذخیره خام، metadata
- Retry، تشخیص block/captcha، ثبت CrawlRun/CrawlError

### FR-PIPE — خط لوله مقاله

State: `DISCOVERED → FETCHING → FETCHED → PARSED → EXTRACTING → EXTRACTED` (+ `IRRELEVANT|DUPLICATE|FAILED|ARCHIVED`)

### FR-AI — استخراج و تحلیل

- کارت استاندارد JSON (بخش ۱۲ پرامپت)
- Relevance، entity، claims، scores
- Dedup چندلایه + Event clustering
- Prompt versioning و cost tracking

### FR-EDIT — سردبیری

- Inbox با فیلترها
- Approve / Reject / Merge / Split / Score / Notes
- اولویت انسانی بر مدل؛ Audit کامل

### FR-POD — پادکست

States: `DRAFT → NEWS_SELECTED → SCRIPT_GENERATING → SCRIPT_READY → SCRIPT_REVIEWED → AUDIO_GENERATING → AUDIO_READY → APPROVED → PUBLISHED` (+ `ARCHIVED|FAILED`)

- متن ۸–۱۲ دقیقه، گفتاری، با منبع برای هر ادعا
- TTS از طریق Adapter؛ Mock در تست

### FR-OPS — عملیات

- Dashboard، jobs retry/cancel، health، usage/cost، settings

## ۷. شاخص‌های موفقیت (KPI)

| KPI | توضیح |
|-----|--------|
| Duplicate removal rate | درصد تکراری حذف/ادغام‌شده |
| Editor acceptance rate | درصد انتخاب مدل تأییدشده توسط سردبیر |
| Factual error rate | خطاهای factual در اسکریپت |
| Mean episode production time | میانگین زمان تولید اپیزود |
| Model cost per episode | هزینه مدل هر اپیزود |
| Articles reviewed | تعداد بررسی‌شده |
| Active sources | تعداد منابع فعال |
| Crawler error rate | نرخ خطای crawler |
| Mean time to discovery | میانگین زمان کشف خبر جدید |
| Editor edit distance | میزان ویرایش متن مدل |
| Clean episode rate | درصد اپیزود بدون خطای سیستمی |

## ۸. معیار پذیرش نسخه اول

نسخه اول قابل‌قبول است وقتی:

1. حداقل ۲۰ منبع مدیریت شود  
2. منابع طبق زمان‌بندی بررسی شوند  
3. مقاله جدید شناسایی و ذخیره شود  
4. متن اصلی استخراج شود  
5. مقاله به JSON استاندارد تبدیل شود  
6. تکراری واضح تشخیص داده شود  
7. رویدادهای مشابه گروه‌بندی شوند  
8. امتیاز اهمیت و اعتبار ایجاد شود  
9. بررسی و تأیید انسانی ممکن باشد  
10. اپیزود از خبرهای منتخب ساخته شود  
11. متن ۸–۱۲ دقیقه‌ای تولید شود  
12. همه خبرهای استفاده‌شده منبع داشته باشند  
13. مصرف توکن و هزینه ذخیره شود  
14. اجرای ناموفق قابل تکرار باشد  
15. خطاهای crawler و مدل در پنل دیده شوند  

## ۹. نیازمندی‌های غیرعملکردی

Idempotent jobs، retry امن، عدم از دست رفتن مقاله، مقیاس Worker، تحمل خطای Provider، تعویض مدل بدون تغییر business logic، جلوگیری از vendor lock-in، تست‌پذیری، log قابل ردیابی، backup، retention، export/delete، UX موبایل، API استاندارد با pagination/sort/filter/search.

## ۱۰. محدودیت‌های حیاتی

1. LLM منبع حقیقت نتایج مسابقه نیست  
2. متن کامل همه مقالات به مدل گران ارسال نشود  
3. مدل گران فقط مرحله سردبیری  
4. هر ادعا در پادکست به منبع وصل باشد  
5. مدل اطلاعات خارج از ورودی اضافه نکند  
6. خروجی AI با JSON Schema اعتبارسنجی شود  
7. شکست مدل → Job قابل تکرار  
8. تصمیم انسانی اولویت دارد  
9. تغییرات سردبیری Audit شوند
